Format: guided walkthrough (speaker's machine; participants do not need a laptop). Revision 4, 27 Oct 2026 (evening), English. Supersedes the Italian run sheet in the design doc (§9) and revision 3 where they differ; the differences are listed at the end. The running example is specified in `00-running-example.md`; this sheet follows it.

Screen layout for the whole session: slides or terminal on the left two thirds, `npm run tail` (formatted `tail -f` on `out/events.jsonl`) on the right third, started before 15:20. Every live command is an npm script with its arguments fixed in `package.json` (`.npmrc` with `loglevel=silent`, so only the tool's output is printed); every live step has a snapshot in `fallback/segN/` shown with `cat` if the command fails. Terminal at ≥ 18 pt, light theme. Git tags: one per segment, checked out at the first live slide of the segment (orange pill on the slide, `ws-seg` + tag in the phase strip): `ws-seg1` before 15:20 (with `npm run log:reset && npm run rag:index`), `ws-seg2` at 15:35, `ws-seg3` at 15:48, `ws-seg4` at 15:59, `ws-seg5` at 16:10, `ws-seg6` at 16:23. `out/` is git-ignored, so the log carries over; the working tree must be clean.

Running domain: art. 2477 of the Italian Civil Code ("Sindaco e revisione legale dei conti"), the rule that says when an s.r.l. must appoint a statutory auditor. Lineage `cc-art2477`, three versions from Normattiva: v7 (in force 21 Aug 2014 – 15 Mar 2019, thresholds by reference to art. 2435-bis), v8 (16 Mar 2019 – 17 Jun 2019, D.Lgs. 14/2019: total assets 2 million EUR, revenues 2 million EUR, 10 employees, at least one limit for two consecutive years), v9 (from 18 Jun 2019, L. 55/2019: 4 million, 4 million, 20 employees). v8 and v9 are ingested live; v7 appears only in the retrieval baseline of segment 1. The texts are official and public; every threshold used by the harness (θ, minimum probe size, sampling rates, promotion thresholds) is illustrative and labelled as such.

Stack (decided 27 Oct 2026): the repository and everything shown on screen are TypeScript (Node ≥ 20, strict, ESM; `AGENTS.md`). The five extractors are Claude-backed agents whose responses are replayed from recorded fixtures; the model id, prompt version and extractor version are recorded in the actor of every `*Proposed` event. No agent framework is used: the ACL, comparator, log, projections and harness are small pure functions and the point of the walkthrough is that they stay visible. If a framework were needed in production, the choice is Strands Agents (TypeScript SDK); it would wrap the extractors only, never the decision path. Types are shown before implementations (slides 7 and 17; `04-domain-model-reference.md` §7, `05-harness-design.md` §7).

## What changed from the Italian run sheet (design doc §9)

1. **Segment 2, review step made consistent with the segment 5 numbers.** The worked example (handbook §6.2) requires claims@v1 to produce, on comma 2 of v8, two correct proposals (`attivo.limite`, `ricavi.limite`), one wrong value (`esercizi.consecutivi` 3 instead of 2), one proposal absent from the text (`capitale.soglia`, the capital trigger abrogated in 2014) and one missing claim (`dipendenti.limite` 10). The run sheet previously said "the CLI verifies the four claims"; it now says the reviewer verifies two, leaves two proposed and adds two by hand. The golden set is still four human-verified items; the eval of v1 against it gives TP 2, FP 2, FN 2 as planned. The fixture for claims@v1 on v8 must be recorded accordingly (`AGENTS.md` §6).
2. **Structure verification made explicit in segment 2.** The Claims ACL accepts only `StructureVerified`, so the claims extractor cannot run until the reviewer has verified the tree. The step is now `extract:structure-v8` → `review` → `extract:claims-v8`. In segment 3 the combined `extract:v9` (structure + claims) works without a review because the v9 tree is reconfirmed by the harness (class A).
3. **Bootstrap promotion of claims@v1.** `npm run log:init` now emits `ExtractorVersionPromoted(claims@v1, actor=human, evidence="initial version")` so that "v1 promoted, v2 candidate" in segment 4 is grounded in the log and not implied. One line in the tail, no extra time.
4. **Batch gate at cold start (segment 3) — needs Luca's confirmation.** The class-A rule requires that the batch passed its probes, and the gate needs probes totalling at least 10 expected items (illustrative). At the moment of the v9 batch the golden set holds four items from one section, and the only possible probe is that section, on which claims@v1 scores TP 2 / FP 2 / FN 2 and would fail the gate (≤ 1 FN, ≤ 1 FP). Running the gate as specified would emit `BatchRejected`, no class-A reconfirmation would occur, and the segment 3 and segment 6 checkpoints would be false. Proposed rule, labelled illustrative and shown in the `npm run compare` output: below the minimum golden-set size the gate is not applicable, class A is decided by the comparator alone, and audit sampling of class-A reconfirmations is 100 % until the minimum is reached. The alternative — skip class A in the workshop — removes the harness-reconfirmation chain that segment 6 depends on. This rule must be mirrored in `src/harness/eval/batchGate.ts` and in the README.
5. **Segment 5, golden set shown twice.** Once with the cut-off after segment 2 (four items, the eval input) and once without (seven expected items, including the three human resolutions of the v9 conflicts), to show property 4 — conflict resolutions enter the golden set — on the log of the session itself. Costs 30 s, taken from the segment 5 framing talk (3 → 2 min).
6. **Segment 2 checkpoint reworded.** "An extractor v4 proposes 4,000,000" is now "a later extraction proposes 4,000,000", to avoid a version number that reappears with a different meaning in segment 4.
7. **Segment 3 debrief** now runs `npm run layers-4-6` (30 s) as the design doc §10 already prescribed, with its fallback file listed.
8. **Segment 5 checkpoint reworded.** With the illustrative Claims threshold at 0.90, v2's precision of 0.60 fails criterion 1 on its own and the question "do we promote v2?" is trivially no. The checkpoint now asks the room to assume the thresholds were met, so that the answer has to come from the per-item drift matrix, which is the point of the segment. The worked numbers are unchanged; `npm run drift:v1-v2` lists both failed criteria.
9. **Temporal query is valid time on stage.** Handbook §4.8 describes "what did we believe on date D" as a fold up to the sequence current on D (transaction time). Every event in the workshop log is appended on 28 Oct 2026, so that fold returns the same thing for any D before today. `npm run beliefs:at-2019-04-30` and `npm run ask:ricavi-2019-04-30` must therefore be implemented as valid-time queries — the belief whose document version is in force on D, using the version's effective date — with `--seq <n>` as the separate transaction-time form. The README and the handbook §4.8 text need the same correction; the repo generator (`AGENTS.md`, `projections/beliefs-at-date`) must implement `--at` as valid time.
10. **`npm run show:ricavi-v8` shows the `ricavi.limite` proposal by id**, since the last appended event is the `capitale.soglia` proposal.
11. **Actor kind for deterministic system steps.** `LogInitialised`, `DocumentVersionIngested`, `ACLRejected` and `CursorAdvanced` are produced by neither a human, an agent, the harness nor an import. The tail prints `process(ingest)`, `process(acl)`; the event schema needs a fifth actor kind `process`, or these events assigned to `harness`. Decision for Luca; the script assumes `process`.
12. **Cold-start gate exemption applies to the Structure layer too.** The harness reconfirms the v9 section tree (class A) in segment 3 under the same condition as the claims: a Structure golden set of one item cannot meet the probe minimum, so revision 4's rule covers both layers. The repo instructions do not state this yet.
13. **Span coordinates on screen.** Handbook §6.2 prints section-local spans ([280, 342) for the total-assets threshold); slide 7 and `npm run show:ricavi-v8` print absolute coordinates ([1,067, 1,126)). `npm run eval:claims-v1` should print absolute coordinates with the section-local form in brackets, so that the IoU arithmetic spoken aloud (62/64) matches what is on screen.
14. **Running domain replaced: art. 2477 c.c., versions v8/v9 from Normattiva, per `00-running-example.md`; all names, values, spans and npm scripts follow the sheet's §11 table.** The previous example is withdrawn from every deliverable; the worked counts of handbook §6.2–6.4 are unchanged (TP 2 / FP 2 / FN 2 and TP 3 / FP 2 / FN 1), the IoU of pair 1 becomes 62/64 = 0.97, the conflicts in segment 3 are three (the three thresholds) and the novelties two (cessation after three years, the thirty-day term), the reconfirmation one (two consecutive years).
